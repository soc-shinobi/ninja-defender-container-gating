# Which scanning tool does what (and is the DevOps connector still the way to go?)

Verified against Microsoft Learn on 2026-09-18, and by installing and running the Defender
for Cloud CLI (`defender scan --help`, v2.0.3334.114). This is the decision the lab is built on.

## Short answer

**Yes, the Azure DevOps / GitHub connector is still valid and still the backbone.** It is
Generally Available. The new Defender for Cloud CLI does **not** replace it. They are
complementary:

- The **connector** gives central, agentless code/IaC/secret/dependency scanning with no
  pipeline changes, DevOps posture, code-to-runtime mapping, Cloud Security Explorer,
  attack paths, and PR annotations. It is also the **preferred, tokenless authentication**
  for the Defender CLI.
- The **Defender for Cloud CLI** is the single Microsoft in-pipeline tool. It is the
  **successor to Microsoft Security DevOps (MSDO)** — the binary self-identifies as the
  "Microsoft Security DevOps CLI" — and orchestrates many scanners under one command. It can
  **break the build** and uploads findings to Defender for Cloud. It needs Defender auth
  (token or connector) even to run.

## What the Defender CLI actually covers

From `defender scan --help` on the installed binary:

| Subcommand | Covers | Scanners it can run |
| --- | --- | --- |
| `scan fs <dir>` | IaC, code, dependencies, malware | checkov, templateanalyzer, iacfilescanner, trivy, bandit, eslint, gosec, flawfinder, spotbugs, binskim, credscan, antimalware |
| `scan image <ref>` | container image vulnerabilities | mdvm (Microsoft Defender Vulnerability Management) |
| `scan model <ref>` | AI model vulnerabilities | modelscanner |
| `scan sbom <ref>` | SBOM generation | (filesystem or image) |

Install: `curl -L -o defender "https://aka.ms/defender-cli_linux-x64" && chmod +x defender`.
Auth: `DEFENDER_TENANT_ID` / `DEFENDER_CLIENT_ID` / `DEFENDER_CLIENT_SECRET`, or connector-based
(no token). Without auth it exits with `AUTH_CONFIG_ERROR` before scanning.

## The scans in this lab

Every scanning workflow uses the Defender for Cloud CLI. No public-action scanners, no
legacy MSDO action.

| Scan | Demo pipeline (`atlas-ci.yml`) | This repo's own CI (`security-defender.yml`) | Central / agentless (connector) |
| --- | --- | --- | --- |
| **IaC / code / deps** | `defender scan fs` (break) | `defender scan fs` (report-only) | agentless code scanning |
| **Image** | `defender scan image` (break) | `defender scan image` (report-only) | ACR registry VA |
| **AI model** | `defender scan model` (optional) | `defender scan model` (report-only; defaults to Microsoft ResNet-50, override on manual run) | AI posture (CSPM) |
| **SBOM + malicious packages** | `defender scan sbom` (optional) | `defender scan sbom .` (SPDX JSON artifact + package inventory summary) | SBOM generated by agentless scanning |
| **Secrets** | GitHub Advanced Security | Defender `scan fs` includes credscan; Gitleaks gates app build contexts | exposed-secrets (needs GHAS) |

Both pipelines use the same CLI for filesystem and image scanning; the demo pipeline enforces
those gates, while this repo reports findings so intentionally-vulnerable code does not turn
CI permanently red. This repo's workflow also demonstrates model and SBOM scans. The CLI
needs Defender auth (`DEFENDER_TENANT_ID/CLIENT_ID/CLIENT_SECRET`
or connector) even to run, so `security-defender.yml` skips cleanly when those secrets are
absent; central coverage then comes from the connector's agentless scan. Gitleaks gates app
build contexts, while Defender's filesystem scan also runs its packaged `credscan` scanner.

## Status notes that matter for the talk

- **Defender for Cloud CLI**: one binary, `scan fs` / `scan image` / `scan model` / `scan
  sbom`. The repo's `security-defender` workflow demonstrates all four commands. It is the
  MSDO successor and runs checkov, templateanalyzer, trivy, bandit, eslint, mdvm and more.
  Needs `DEFENDER_*` auth or a connector even to run.
- **MSDO CLI**: legacy, in maintenance support. Do not add it; the Defender CLI replaces it.
- **Secrets**: GitHub Advanced Security provides platform scanning; Gitleaks gates app build
  contexts, and Defender `scan fs` includes its packaged credscan scanner.
- **No public-action scanners in any workflow**: every scan runs through the Defender CLI.
  A fork that has not set the `DEFENDER_*` secrets gets no in-CI scan (the job skips); its
  coverage comes from the connector's central agentless scan instead.
- **Agentless code scanning**: connector-based, default branch, daily, cannot break builds.
  This is the "covers the team that never adopted shift-left" path.

## Code-to-runtime mapping (the "hero digest")

Defender maps an image back to its repo and commit by one of three methods
(https://learn.microsoft.com/en-us/azure/defender-for-cloud/container-image-mapping):

1. **DevOps connector** — automatic once GitHub/ADO is connected. Microsoft's wording:
   connecting the environment triggers a set of automated tools that *"do not affect your
   existing DevOps workflows and enable code-to-runtime mapping"*. No pipeline edits, org-wide.
   Caveat: images built and deployed **before** connecting may have limited mapping support.
2. **Docker labels** — OCI `org.opencontainers.image.source` / `.revision` stamped at build
   time. The Atlas `image` job stamps these, so mapping works even without the connector.
3. **GitHub attestations** — cryptographic build provenance from GitHub Actions.

Important for the bypass beat: **manually built-and-pushed images are not supported** for
code-to-runtime mapping. The Docker Hub bypass image therefore shows up only in runtime VA,
not in the code-to-runtime chain — which is exactly the point.

## One connector caveat (newer preview)

There are now two connector experiences:

- **Azure portal GitHub connector** — GA. This is what the lab uses. `make connect-github`.
- **Defender portal GitHub connector** — private preview, aimed at agentic code security.

You cannot have both on the same GitHub org at once. If you connect the org in the Defender
portal, disconnect the Azure portal connector first (and vice versa). For this demo, stay on
the Azure portal GA connector.
